## 1. 协作概况

### 1.1 任务背景与目标

本项目在 xc7z020clg484-1 上实现「四路 INMP441 麦克风阵列时域互相关测向 + 八方向 LED/舵机指向 + OV5640 摄像头与 Light-ASD 视觉确认 + 振动提醒」的听障辅助感知终端。大模型被用于以下环节：

- **只读代码勘察与故障定位**：能量 VAD 误触发、LED 乱闪、时序不收敛、bitstream 与源码不一致等；
- **RTL 改进代码生成**：在独立目录生成采样级 VAD、相关可信度门控、5 帧表决等 `*_v2` 文件，原工程只读、约束不改；
- **时序收敛迭代**：根据 Vivado routed 报告逐轮拆拍流水线；
- **参数核算**：3.5 cm 阵列最大 TDOA、采样率、门限时间换算等；
- **需求纠偏与方案取舍**：纠正模型扩大需求、否决越界技术路线；
- **经验提炼**：沉淀可复用技能包、提示词模板与踩坑清单。

使用边界：AI 为辅助工具，负责人提出目标与约束、提供板上现象、执行仿真/综合/上板验证并做实测采信与最终取舍；一切硬件结论以 Vivado 报告与板上实测为准。

### R1（成员 C）LED 顺序是否写反
- **协作目标**：灯的顺序是 73516240，是不是代码写反了。

### R2（成员 C）J35 信号脚电压之辩
- **协作目标**：确认 J35 信号脚是 1.8 V 还是 3.3 V，两个模型说法不一致时信谁。
- **提示词摘录**：
  > 你怎么确定的 J35 的给信号的地方是 1.8 V 不是 3.3。GPT 还是说是对的，到底你厉害还是他厉害。
- **类型**：事实核实。**模型与模式**：Cursor 助手。
- **回答要点**：
  1. 模型认为第 1 针为 3.3 V、第 13 针为地；需结合原理图版本和连接器观察方向核对；
  2. 模型按当时手册读法推断信号针属于 1.8 V Bank；原理图、VCCO 和对应实测未在本次材料中提供，暂不确认；
  3. 万用表量到第 1 针是 3.3 V，不能证明旁边的信号针也是 3.3 V（被采用，方法论要点）。
- **自我纠错（后续补记）**：麦后来仍接在 J35 上且方向灯能对上，总工程约束即 J17、J16、L17、M17；「信号脚是不是 1.8 V」电气上没有再用万用表复核，保留这次分歧，不能以“方向灯能亮”证明电气兼容；当前 XDC 指定 LVCMOS33，与原稿的 1.8 V 判断需要结合实际板卡 VCCO、引脚和接线重新核对。
- **证据状态**：原稿记载查阅手册且只测过电源针，信号电平仍未核实。**采纳程度**：修改后采用。**截图**：F1，见 Word 记录中的截图附录。

### R8（成员 C）360° 舵机与「上」的定义
- **提示词摘录**：
  > 我现在买的舵机好像是 180 度旋转，那我可以买 360 度的吗，因为我觉得旋转是否有点受限了。
  >
  > 我的麦克风是一整个放在桌上，用面包板串联的。规定了八个方向。它的那个上，是正上方吗，也就是立体的 Z 轴吗？我的舵机是这么写的吗？还是说这个方向其实是规定的一个平面？
- **类型**：事实核实 / 方案取舍。**回答要点**：
  1. MG90S 靠脉宽定位、行程约 180°；卖家标题「360°」说的是支架（被采用）；
  2. 市面 360° 舵机多为连续旋转：1.5 ms 停、脉宽一偏就一直转，停不住「左/右上」；云台支架和线也不允许转满一圈（被采用——**否决换 360° 连续旋转舵机**）；
  3. 平面麦阵的「上」是桌面上的一个方向，人站天花板正对麦阵中心喊时四路几乎同时到、接近无方向（被采用）。
- **自我纠错**：演示只站前半圈；俯仰抬头改为只转水平舵机 J3；立体麦阵未做。后换标称 270°、仍靠脉宽定位的舵机；报告不把 ±120° 写成量角器量过（原稿另记商品页行程约 200°±5°，其与实际 270° 舵机是否为同型号未核实）。
- **核实状态**：商品页截图核实（见 F6、F7；是否对应现用舵机型号仍需核对）。**采纳程度**：修改后采用。**截图**：F4、F5，见 Word 记录中的截图附录。

### R9（成员 C）上电发热、针序、脉宽位宽

  >

### 4.3 典型纠错案例详述

#### 案例 1：振动时机——模型建议与总工程取舍相反（R6 / H2）
1. **问题现场**：模型答「马达被解释成『有人在叫』的提示，应该跟着声音走……等摄像头确认再震，对人来说太慢」，并给出 60 秒灯带确认时序。
2. **为何错误**：与总工程的实际取舍相反——最终逻辑是视觉确认通过后 J6 才拉高约 300 ms；声音单独成立不振；当时的比特流不点灯带、无 60 秒计时；当时采用约 2 秒的结果有效期；当前发布源码已将上限改为 120 秒，不能沿用这条旧规则描述当前版本。
3. **查证过程**：作者对照总工程当时的比特流的真实行为逐条核对。
4. **正确写法**：确认通过后振动；声音路径不振。
5. **采用去向**：总工程 J6 逻辑；报告中不再出现「一有声音就震、灯带变红」。

#### 案例 2：时序收敛链——从 −14.468 ns 到 +0.599 ns（R16-5、B2 / S6）
1. **问题现场**：新 VAD 首次综合「布线后最差建立时间大约 −14.468 ns」。
2. **为何错误**：滤波、平方、42 位累加和阈值比较放在同一拍，形成超长组合路径。
3. **查证过程**：读 Vivado routed timing 定位关键路径；先拆 hop 判决两拍（−7.942 ns，仍不够），关键路径转移到滤波/平方/累加；再将每个样本拆为 HP、LP、平方、累加四拍。
4. **正确写法**：采样级多拍流水线；独立改进版 WNS +0.599 ns / WHS +0.041 ns，当时的 tdoa2 WNS +0.420 ns / WHS +0.023 ns（100 MHz、routed）。
5. **采用去向**：tdoa2 工程；《优化过程与性能资源对比.md》§6 迭代表、§8 资源时序对比表；资源代价 LUT +36.9%、FF +48.6%、DSP +80%、BRAM 0，最终占用 LUT 4.62%、FF 1.98%、BRAM 5.36%、DSP 4.09%。

#### 案例 3：需求越界——「完整音视频融合仍未接入」（R15 / H6、S8）
1. **问题现场**：模型输出把「完整音视频模型融合」列为还没做完的项。
2. **为何错误**：作者从未要求接入音频神经网络；需求边界是「芯片内部接收并判断」，麦克风侧保持能量检测与互相关。
3. **查证过程**：作者直接质问「我也没说要接入音模型啊」；模型承认扩大需求。
4. **正确写法**：正式判断留在片内 ARM——YuNet 找脸、Light-ASD 只留视觉分支；原稿记载换官方 Light-ASD 后同批离线样本 70.3%→90.6%、纯视觉分支 360 条 87.5%，均标注为离线成绩，非板上、非自动找脸后成绩。
5. **采用去向**：报告-软件章节；「没有交给模型改掉的事」清单同步写明测向保持时域互相关、未换 GCC-PHAT。

#### 案例 4：「板上生效」与「代码存在」混写（R16-6、B4 / S7、H8）
1. **问题现场**：作者报「灯不亮」，此前板测现象被默认可用于评价当前算法。
2. **为何错误**：源码修改时间晚于 bitstream，板上跑的不是当前算法；「单独综合通过」「整片布线通过」「烧录成功」「板上验收」是四件不同的事。
3. **查证过程**：Codex 核对 RTL 与 `.bit` 时间戳及文件内容；发现融合工程仅 OOC 综合（WNS +1.08 ns、routed=false、board_verified=false）。
4. **正确写法**：先对时间戳与内容再重新实现；旧比特流现象作废；新增 `parse_vivado_reports.py` 新鲜度检查；旧比特流移入 `integrate/old_bit_do_not_program/` 禁烧。
5. **采用去向**：优化文档 §3 瓶颈定位表「bitstream 时间戳/哈希检查」；原稿的整合版记载 WNS +0.244 ns；独立重建副本以 build/reports/ 中 WNS +0.333 ns 的实际报告为准；当前下载文件沿用原 integrate 工程配套产物。

## 5. 智能体工作流设计

> 判定：本项目**部分使用**智能体工作流。成员 B 在 Codex 上以 Agent 模式运行了「只读勘察 → 假设 → 独立目录生成 → 仿真 → 综合/实现 → 报告解析 → 板测回流」的闭环（具备任务编排、多环节工具调用与输入产出流转）；成员 A、C 使用 Cursor 助手做多轮对话与多文件阅读，未启用自动执行。**未把任务拆分给多个智能体协作，故不设多智能体分工。**

### 5.1 使用范围与目标

- **使用自动化的任务**：tdo/tdoa2 麦克风链路的误触发定位与改进代码生成、时序收敛迭代、参数核算、Vivado 报告解析与 bitstream 新鲜度检查、通用 PYNQ/AXI 技能包制作、优化过程与协作记录整理。
- **目标**：在不覆盖原工程、不修改 XDC 的前提下，产出可独立验证的补丁，并把「代码存在」与「板上生效」严格分开。

|---|---|---|---|---|---|---|

### 5.3 协作流程

工作流程：需求与约束 → 只读代码勘察 → 提取参数和证据 → 提出可验证假设 → 独立目录生成补丁 → 仿真 → 综合与实现 → 核对报告和 bit/XSA → 人工上板验收 → 整理工程与技能。

仿真或时序失败时返回补丁阶段；源码与产物不匹配时先重新构建；板上现象与预期不符时返回假设与证据核对阶段。

### 5.4 人机分工、闭环与局限

- **AI 承担**：多文件只读勘察、把代码事实与推测分开、在独立目录生成可独立验证的补丁、根据时序/资源报告迭代、识别「旧 bitstream」「OOC 不等于上板」「表决语义偏差」等隐蔽问题、把经验整理成脚本/提示词/案例/踩坑清单。
- **作者承担**：提供目标、约束、板上现象与硬件连接；审阅 Vivado 工具结果并执行上板测试；实测采信与最终取舍；需求边界守门（如否决音频网络）；报告定稿。
- **纠错闭环**：仿真/综合拦截功能与时序错误（拆拍迭代 3 轮）；报告解析器拦截「旧 bitstream」类证据失效（1 次板测结论作废重跑）；人工打回 2 次（需求越界、左右对调方案）；失败实验结果保留不覆盖。
- **效果与局限**：效率提升在多文件勘察、时序迭代的机械性拆拍、参数核算与文档整理；自动化失败点在技能脚本首跑（WSTRB 位宽/握手错误，修复后通过）；必须人工兜底的环节是板上现象判读、需求边界守门与实测采信。**下次项目值得复用**：只读勘察→独立目录→报告解析→新鲜度检查这条闭环；需改进处是要求模型每轮标注证据等级，减少人工二次核对。

## 6. 协作成效、边界与反思

### 6.1 合理使用情况

- **多文件勘察提速**：Codex 只读 tdo 工程即定位「能量阈值过低、重叠帧确认短、无相关门控、LED 保持 0.5 s」四项候选原因（R16-2、B1）；
- **时序迭代的机械性工作**：拆拍流水线的方案与验证循环由模型驱动，人工只做上板确认（案例 2）；
- **参数核算**：3.5 cm 阵列最大 TDOA ≈ 4.98 采样、单采样声程 7.03 mm、hop=480 ≈ 9.83 ms 等换算原稿称已核算，阵列间距与声速假设仍应附依据（B3、优化文档 §4/§5）；
- **记录结构化与语言整理**：本协作记录、优化对比表、性能 CSV 均由模型在人工核对数据后整理生成（R16-10）。

### 6.2 不足与问题

- **被否决的方案**：换 GCC-PHAT（C、B 均只做增强观察，未改路线）、加音频神经网络（A5）、换 360° 连续旋转舵机（R8）、单纯降低 VAD 门限（B1）——均如实保留否决原因；
- **模型错误与越界**：记录包括需求越界（案例 3）、置信度表述无依据（H7）、技能脚本首跑失败（H10）、前次回答表述笼统后改口（S1）；由于记录有主题归并，不按条目数统计事件总数；
- **记录缺失**：成员 B 的提示词只有本人摘要、无逐字记录与截图；成员 C 的七项问题汇总部分与前述截图事件重叠，剩余内容仍缺原始对话；C7 无单独插头照片；3.5 cm 间距无实测照片；Cursor 所用模型名称/版本未记录；
- **未完成事项**：板上验收矩阵（人声/音乐/风扇/敲击/静音）未完成；八方向正确率和误提醒率仍待统计。

### 6.3 提示词改进方法（结合纠错轨迹总结）

1. **开头就给红线与约束**：「不覆盖原文件、不修改约束、要能上板」有助于限制改动范围，但不能据此宣称零事故——对应 H8/H10 的教训来源；
2. **要求区分证据等级**：把「仿真/综合/routed/烧录/板测」分开记录的要求写进提示词后，有助于避免把 OOC 结果混写成总工程时序，效果仍需逐条核对——对应案例 4；
3. **一次只改一个维度**：B3 参数调优每轮只动一个参数并记录前后，避免多变量归因困难——对应 S4/S5；
4. **明确需求边界并要求复述**：「我也没说要接入音模型啊」式直接纠偏，比事后删改更省轮次——对应案例 3；
5. **现象 + 已排除项一起给**：用户提供的直插和转动现象促使重新核对针序；供电定义仍需原理图和测量确认——对应 S2。

### 6.4 人机贡献边界声明

最终方案决策、工程实现、板上实测、数据真实性与报告质量由三位作者负责；大模型（Cursor 助手 / Codex 智能体）承担代码勘察、草拟补丁、时序迭代建议、参数核算与文档整理辅助，不替代作者的实测采信与判断。正式报告应逐项核对器件参数、性能与结论的依据；本文保留的历史摘要不等于已完成独立核验，证据缺失处明确标注待补。

### 6.5 当前发布工程的复现方法

历史 `tdo/tdoa2` 的调试过程用于说明协作方法；实际复现应使用本仓库文件。当前 board/artifacts/ 已提供原 integrate 工程配套的 XSA、bit、ELF 和 PS 初始化脚本，使用这套文件无需先重建 ELF；文件来源与哈希见 build/reports/artifacts.json 顶层字段。以下同时列出按需从源码重建的步骤，独立重建证据归于 rebuild_validation。

1. 按根 README 准备 Vivado/Vitis 2025.2 和匹配板卡，检查 DDR/MIO、接线及 board/xdc/。阵列实际间距应由实物确认，不能只引用历史摘要。
2. 在仓库根目录执行 `python -B sim/run_regression.py`，需要 Python 和 iverilog/vvp。
3. 如需从源码重建硬件，执行 `vivado -mode batch -source build/create_project.tcl` 建立独立工程，检查 BD 和约束后，执行 `vivado -mode batch -source build/build.tcl` 生成 bit/XSA 及报告。两份脚本已在同级 test 副本中实跑成功。
4. 查看 build/reports/ 的时序、资源、DRC、总线偏斜、布线及哈希记录。独立重建副本 WNS=0.333 ns、WHS=0.043 ns；外设 I/O 延时约束仍有不完整项，不能据此宣称所有接口均已验收。
5. 使用现有文件时，选用 board/artifacts/ 中的配套 bit、ELF 和初始化脚本。仅在修改源码或重新生成硬件后，按 board/README.md 使用对应 XSA 更新平台并重新编译；权重按实际使用的 ELF 日志与符号加载。
6. 加载配套 bit/ELF 和 data/weights/ 两份权重后，由作者完成方向、静默/说话、有人脸/无人脸等实物测试并记录结果。独立 Vivado 构建记录的范围为硬件构建，当前发布沿用原工程已有 ELF。
